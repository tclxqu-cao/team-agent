# 企微本地库静态资料读取（群列表 / 群成员 / 全量通讯录）

> 基于 `reader.py` 的离线读库能力（2026-11-11 完成全量姓名）。不碰企微进程、不改原库/WAL、不需要 root。

## 结论

- **全量通讯录在 `Messages1/Session.db`**（与 Info.db 同目录、同 VID key），`USER` 表 7 万+ 行（RID=VID、name、job、corpid、alias…）+ `DEPARTMENT`（部门树）+ `MYHEAD`（UID→部门）。**不需要 `Contact/Contact.db`**（该库 key 走服务端授权，本地解不开，也没必要）。
- 消息 senderName 覆盖率 **99~100%**（原 CONVERSATION join 只有 42%）。
- 群成员（`CONV_MEMBER_DATA.member_bin` protobuf：f1=VID/f2=加入时间/f3=邀请人VID）姓名覆盖 **100%**（5096/5098）。

## 用法

```bash
cd packages/messaging/assets/wecom
CFG='{"database":"<Profile>/Messages1/Info.db","accountId":"<VID>","cacheDir":"/tmp/wecom-static"}'
printf '%s' "$CFG" | /usr/bin/python3 reader.py --contacts          # 全量通讯录 VID→姓名/部门/职位
printf '%s' "$CFG" | /usr/bin/python3 reader.py --groups           # 全量群列表（含群主）
printf '%s' "$CFG" | /usr/bin/python3 reader.py --members <群RID>   # 群成员（VID+姓名+邀请人）
printf '%s' "$CFG2" | /usr/bin/python3 reader.py                    # 消息增量（含 senderName）
```

`read_batch` 每条消息新增 `senderName`（USER 表优先，CONVERSATION.name 兜底）；`session_plain()` 自动解密 Session.db 并按 mtime 缓存（删除 `cacheDir/Session.db.plain` 可强制刷新）。

## 踩坑记录

1. **Contact.db 误判**：曾以为"群成员姓名需要 Contact.db 第二把 key"——实际 **Session.db 就是全量通讯录**，同 VID key 直接解。Contact.db 是受保护库（key 走服务端授权 vid/st/cst/deviceid 链，本地穷举 240 万次失败），但它没有独特数据，不必碰。
2. `member_bin` 顶层是 field 0（`fields(..., allow_zero=True)`）；内容只有 VID，无姓名——姓名必须 join USER 表。
3. `reader.py` 用 `prepare_mirror` 写死了消息库校验（`quick_check('MESSAGE')`），解其它库要用底层 `frozen_source + decrypt_page` 手动解（见 `session_plain`）；`frozen` 临时目录需预先创建。
4. USER 表没有 departmentid（部门关联在 MYHEAD：UID→departmentid，一个用户可多部门取第一个）。
5. FTS5 表（`*SEARCH*`/`TINYHOT`）依赖 ICU tokenizer，无法在系统 sqlite 里 count——按表名跳过。
