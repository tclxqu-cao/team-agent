# AgentRoam 协作群设计草案

日期：2026-10-14。状态：用户补充历史记录布局与 DDD 要求后进入实施。

## 用户目标与已确认选择

在左侧“新建会话”上方增加“拉群”入口。用户选择一名群主和其他成员，所有参与者都来自 AgentRoam 已接入的 Agent。创建后打开独立的应用内页签，左侧展示群主、成员及职责，右侧展示群消息、协作过程与最终成果。

同一种 Agent 允许加入多个成员，分别选择模型、填写名称和职责；这一点已获用户明确确认。成员以独立 memberId 区分，不能按 Agent 类型去重。群主也是一个独立成员，成员选择器只排除这名群主本身，不排除与群主相同的 Agent 类型。

未填写的职责由群主收到任务后分配。用户明确填写的职责与限制优先，群主不得自行覆盖。群主自主决定任务拆分、依赖、执行顺序、并行、返工和成果汇总，也可以承担具体任务。

## 方案比较

| 方案 | 优点 | 代价与适用边界 |
| --- | --- | --- |
| 在统一会话层新增协作群调度，复用各 Agent 的实际运行时（推荐） | 群主与成员可跨 Agent 类型；保留原生会话、模型、工具及审批语义；可恢复群记录 | 需要新增群领域、持久化调度与实时界面 |
| 直接扩展现有 SubAgentDispatcher | 已有派发、子会话、完成通知能力，上手成本较低 | 当前实现创建内置 AgentBuilder 子实例，不能直接满足任意原生 Agent 当群主和成员 |
| 用已有 Flow Studio 承载 | 可复用工作流可视化和部分运行记录 | 引入另一套服务与资产模型，且原有 CA 动态团队不等于跨原生 Agent 的群协作 |

推荐第一种，保留现有运行时与 UI 组件，新增群协作的业务层。

## 创建与界面

“拉群”打开创建面板，填写群名、选择项目或工作目录、选择群主，再添加至少一名成员。每人可设置显示名称、Agent 类型、模型和职责；模型选项由对应运行时实际提供。不可用的运行时显示原因，不能悄悄替换为其他 Agent。模型不支持单独配置时明确显示“沿用运行时默认”。

创建时默认使用当前选中的项目；没有有效目录时要求选择目录。群配置和历史绑定宿主机保存。两个群即使使用相同 Agent 类型，也不共享成员会话。

群设置提供最大并行运行数，默认取群人数与 3 的较小值，可在空闲时调整。该值包含群主正在进行的规划或执行轮次；群主决定实际并行哪些任务，服务端保证不超过上限。

Web 控制台创建后打开顶部“群名”页签，同一群重复打开时聚焦原页签。群页面左栏展示群主、成员、职责、当前任务和状态；右栏按时间显示用户任务、群主安排、成员汇报、失败与返工、最终成果。成员点击后可查看详细执行轨迹。底部保留群消息输入。

左侧群成员下方固定展示“群聊记录”，按更新时间倒序列出本群讨论记录，显示标题、时间和运行状态。一个讨论对应一条独立记录，拥有独立消息与任务上下文；继续追问沿用当前讨论，点击“新讨论”才创建新记录。点击历史记录后，右侧恢复该讨论的完整消息、步骤和成果；刷新或重开群后仍可读取，查看历史不启动新运行。

成员状态包含空闲、规划中、执行中、等待依赖、等待用户、失败。群页面顶部提供停止和继续。手机端将成员栏收为抽屉，群消息与输入保持可用。

在智能助手侧栏增加可重新打开的协作群列表。关闭页签只关闭视图，后台继续运行；刷新后可重新打开同一群、读取同一运行记录。

桌面端复用群创建和群页面组件，通过现有服务桥接访问同一协作后端；独立运行的桌面端使用应用内群页签承载。桌面端和 Web 端查看同一群时读取同一份数据。

## 协作流程

1. 用户在群里发送目标。服务端先保存消息和本次运行，再唤醒群主。
2. 群主阅读成员配置、用户限制、工作上下文和已有成果，为职责留空的成员分配定位，形成步骤和依赖，给出当前可执行的任务。
3. 服务端校验任务指向的成员、依赖和可用状态，执行符合条件的任务。独立任务可同时开始；依赖未满足的任务等待。群主决定业务顺序，服务端负责依赖和资源约束的实际执行。
4. 成员使用独立真实会话完成任务。群中显示开始、重要进展、步骤结束和产出；详细工具轨迹可展开。工具执行结束与完整步骤完成分别标记，避免将单个工具成功误认为任务完成。
5. 每次成员完成或失败，服务端先保存结果和群消息，再向群主投递持久通知。群主空闲时自动处理；同时到达的通知可合并到一次规划。群主正在执行时，通知进入邮箱，之后继续处理。
6. 群主检查结果，决定安排下一个成员、继续并行、返工、接管或向用户提问。没有新事件时不持续空转调用模型。
7. 所有必要步骤完成后，群主在群中发布最终结果、实际产物链接、验证依据和剩余问题。仍有活动任务或未解决阻塞时，服务端拒绝将整次协作标为完成。

同一成员同一时刻只运行一个会话轮次。群主承担具体任务时，不能同时在同一会话中启动规划轮次；其他成员可继续并行。忙碌时的新用户消息先持久化，再进入群主邮箱；用户停止操作立即进入取消流程。

## 跨运行时的群主控制

群主沿用用户选定的真实 Agent 和模型。规划轮次使用统一的结构化协调协议，表达职责分配、派发任务、依赖、等待、向用户提问和最终交付。成员的普通发言及工具输出不会被当作调度指令执行。

服务端只接受当前群主、当前运行、当前规划轮次的有效决策。协议校验覆盖成员归属、任务唯一标识、依赖存在性、循环依赖、重复派发和并发上限。语义不清或不合法的决策不执行，先反馈群主修正；同一决策最多修正一次，仍失败则保留错误并转为等待用户处理。

原生适配器目前没有统一的额外工具注入参数，因此首版采用规划轮次的结构化结果协议，避免假设所有原生 Agent 都支持同一种自定义工具接口。规划结果从原生会话真实终态输出提取。群主执行具体任务时按普通任务轮次运行，结果回到下一次规划。

成员模型参数、工具权限和人工审批继续由对应运行时执行。职责文案用于协作定位，不能当作文件系统或工具权限隔离。需要真实权限限制时，以运行时实际支持并能验证的选项为准。

## 代码与工作目录并发

不同成员拥有独立会话，不代表文件系统天然隔离。多人修改同一个工作目录前，服务端必须处理目录并发。

同一共享目录的写入步骤默认独占；声明 readOnly 的纯分析或只读任务可以并行，写入步骤须等待读者退出。readOnly 是协作约定，不是系统权限沙箱。群主也可让已隔离目录中的任务并行。需要并行改同一仓库时，为相应任务准备独立 worktree，并将各自实际工作目录交给运行时，随后由群主安排汇总与冲突处理。无法安全准备隔离目录时自动排队，并在群中说明等待原因。

隔离 worktree 不自动包含未提交与未跟踪内容；启动前必须选择并保存可复现的任务基线，保留原工作区改动。不能把“基于旧 HEAD 建了 worktree”当作“基于用户当前项目状态”。对不支持相应隔离能力的目录，首版保守串行。

此约束防止常规协作中的目录冲突，不承诺普通工作目录或 Git worktree 提供操作系统级安全沙箱。浏览器、设备和其他排他资源按实际能力串行使用。

## 状态、存储和恢复

群领域独立保存群、成员、讨论、消息、步骤、待规划标志和 generation。每个讨论中的成员按 memberId 与工作目录绑定专用 sessionId；步骤 ID 在讨论内唯一，新尝试使用新步骤 ID。群会话与普通会话列表按归属区分，避免在左侧重复堆积内部成员会话。

群和讨论快照由 SQLite 持久化，每次事务更新递增 revision。页面每 1.2 秒按 revision 读取变化，轮询不启动执行。持久的待规划标志、步骤 ID、调度租约和工作目录读写租约控制派发，服务端每秒调度，关闭页面不影响执行。重复消息 ID、重复终态事件和多页面读取不造成重复派发。

服务重启后恢复群配置、消息、步骤和已保存成果；发现未确认结果的规划或活动步骤时，当前实现中断对应会话，将讨论标记为 interrupted。用户点击继续后，群主先核对之前的结果再重新安排；不自动重放未知结果的步骤。

停止先将协作运行置为取消中，禁止新派发，再中断群主及活动成员；确认终止后标记已停止。群记录不采纳停止后的迟到结果，不得再次唤醒已停止讨论；底层会话保留其已有运行记录。

人工审批与提问通过群消息展示并绑定真实 questionId 和成员会话；沿用现有权限执行路径。单个成员失败先交群主处理，不将运行时退出或收到一段文字等同于业务成功。

成果引用真实消息、实际文件或已有产物存储，保留生产成员、步骤和尝试来源。没有实际生成文件时只展示文本，不能虚构路径或下载链接。

## 当前代码接入依据

- `packages/desktop/renderer/App.tsx`：当前“新建会话”入口所在，共享于桌面与 WebApp。
- `packages/webapp/src/main.tsx`：导入共享 App，也是独立群页面视图的 WebApp 接入位置。
- `packages/server/app/web/page.tsx` 与 `console-tabs.ts`：现有智能助手、AI Hub、Flow Studio、远程桌面的页签承载层。
- `packages/desktop/renderer/global.d.ts` 与 `packages/webapp/src/infrastructure/http/agent-http-gateway.ts`：共享 AgentApi 与 HTTP 桥接。
- `packages/native-runtime/src/agent-runtime/types.ts`：现有 AgentType、模型选择、创建与运行接口。
- `packages/native-runtime/src/agent-runtime/unified-session-service.ts` 与原生 broker：原生会话执行、逐会话互斥、事件和审批基础。
- `packages/server/lib/native-runtime-service.ts`：原生运行服务入口。内置 Customer Agent 由 agent-host 管理，需要在群执行端口中单独路由，不能假定它已注册到此原生服务。
- `packages/native-runtime/src/sub-agent-dispatcher.ts`：可参考派发、独立子会话和父会话通知模式；其 AgentBuilder 子实例不直接替代跨运行时群成员。

实现必须遵循 DDD。群聚合、成员、讨论、任务状态和依赖规则放在 core/domain/collaboration；调度用例与执行、仓储端口放在 core/application/collaboration，领域不依赖 React、Next.js、SQLite 或具体 Agent 适配器。SQLite 仓储和运行时执行适配器在基础设施层实现，由服务端组合内置 AgentHost 与原生 broker；HTTP 路由只承担请求校验、鉴权和调用应用服务。UI 通过 API 使用用例，采用独立群组件，避免继续扩大现有 ChatView。依赖规则、任务转换、取消与完成条件不能散落在路由或 UI 中。

## 验收条件

1. “拉群”位于“新建会话”上方，可创建独立页签、关闭、重开和刷新恢复；重复打开同一群不复制页签。
2. 能同时添加多个同类型 Agent，分别配置模型和职责；群主成员身份不会重复加入。
3. 职责留空后由群主真实分配，用户预设职责不会被覆盖；每人有独立真实 sessionId。
4. 用真实可用 Agent 验证一次跨类型协作和一次同类型多成员协作，保留运行、成员会话和消息证据。
5. 至少两个没有依赖的任务实际同时运行；后继任务在依赖完成后自动开始。共享可写目录排队、隔离目录并行均有验证。
6. 成员步骤完成、失败、重试和人工提问会出现在群中，自动唤醒群主，不需要用户逐次点击继续。
7. 重复完成事件、页面轮询和双页面读取不造成重复派发；非法依赖、忙碌会话和停止后迟到事件均有回归覆盖。
8. 关闭页面继续执行，重新打开可追踪同一运行；服务重启恢复不盲目重跑未知结果的任务。
9. 最终成果包含实际产物与验证结果；有活动步骤或阻塞时不能提前宣告整体完成。
10. 桌面与手机布局、原有新建会话和普通 Agent 聊天通过必要回归。构建通过与真实协作验收分别报告。
11. 左侧群成员下方可看到持久群聊记录，点击后恢复对应讨论；创建新讨论不会串入旧讨论的消息与任务，刷新后历史仍可查看。
12. 领域与应用层不导入基础设施或表现层，群规则由领域测试验证，调度通过端口替身验证，持久化与 HTTP 另做集成验证。
