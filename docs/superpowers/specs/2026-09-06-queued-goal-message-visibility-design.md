# 排队目标消息可见性设计

## 目标

目标模式保持串行执行。活动目标立即显示在会话消息区；后续目标在等待期间只显示于目标队列，被提升为活动目标后才显示在会话消息区，避免同一目标同时出现在两个区域并造成“已经执行”的误解。

## 状态与展示

目标提交继续创建带稳定 `sourceMessageId` 的本地用户消息，并通过现有接口进入持久目标队列。消息数据仍保留在逐会话 store 中，以维持附件、Agent 标记、历史合并和去重契约。

渲染消息列表前，根据 `goalState.queued[*].sourceMessageId` 建立等待目标消息 ID 集合，并暂时过滤这些用户消息。首个目标会被服务端立即提升为 `active`，因此正常显示；等待目标被提升后离开 `queued`，无需复制或重建消息即可自动显示。

该规则只影响目标消息。普通排队消息继续使用现有排队栏和 `isQueued` 展示逻辑，历史中的已执行目标也不隐藏。

## 生命周期边界

- 排队目标删除成功后，同时从对应会话的本地消息 store 删除其隐藏消息，防止目标离队后消息意外显现。
- 活动目标停止后保留用户消息，因为它已经进入执行历史。
- 目标入队失败时删除本次乐观创建的用户消息，并保留现有错误提示。
- 页面刷新后，尚未执行的目标由持久队列恢复，且不会凭空生成会话消息；开始执行后以原生历史或当前会话中的稳定本地消息显示。
- 后台会话的状态同步继续遵守逐会话隔离，不得覆盖当前浏览会话。

## 实现范围

- `packages/desktop/renderer/components/ChatView.tsx`：计算等待目标消息 ID、过滤消息区、处理排队目标删除和入队失败清理。
- renderer 测试：覆盖活动目标可见、排队目标隐藏、提升后显示、删除与失败清理，以及普通消息不受影响。

不修改目标队列排序、Broker 自动接力、原生运行时协议或目标完成判定。

## 验证

- 运行受影响的 renderer 单元测试和 Desktop/WebApp TypeScript 检查。
- 检查现有目标队列、消息历史合并和普通排队消息回归。
- 在移动端宽度验证：一个目标执行时发送第二个目标，第二个只出现在目标队列；首个目标完成后，第二个进入消息区并开始执行。
