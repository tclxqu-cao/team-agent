# Codex Cross-Version Session Compatibility Design

## Goal

AgentRoam must keep every active Codex session under the effective `CODEX_HOME` visible across Codex Desktop and CLI version differences. A session that the selected runtime can safely resume continues in place. A session that cannot resume in place but can be losslessly normalized continues through an explicitly labelled migration copy. A session that cannot be read or migrated safely remains visible and reports a structured version-compatibility reason instead of disappearing.

The change is additive. The existing Codex App Server discovery, workspace association, pagination, ordering, occupancy, fork, deletion, goal, permission, and live-follow behavior remains authoritative for sessions it already returns.

## Scope

This design covers active rollout files below `$CODEX_HOME/sessions`. `CODEX_HOME` continues to resolve from a non-empty environment value and otherwise defaults to `<homedir>/.codex`.

Archived Codex sessions remain governed by the existing product behavior and are not added to the active sidebar by this change. Claude Code, OpenCode, and Customer Agent session formats are unchanged.

## Current Behavior And Risk

`CodexRuntimeAdapter` launches the executable selected through `AGENT_CODEX_BIN` and discovers sessions through paginated `thread/list` calls. The CLI runtime manager currently requires the exact managed Codex version `0.153.0`. The App Server result is therefore produced by a fixed reader even when another Codex client wrote the rollout with a different version.

Codex rollout `session_meta` records include `payload.cli_version`. Local evidence also shows multiple historical record shapes and many stable and alpha producer versions. The App Server schema generated by Codex is specific to the generating Codex version; there is no cross-version forward-compatibility guarantee on which AgentRoam can rely.

The current failure mode is silent omission or a broad native-protocol error: a rollout may exist on disk while `thread/list` does not return it, and the renderer cannot distinguish an unsupported producer format from an absent session.

## Design Decision

Use a hybrid compatibility strategy:

1. Keep the current App Server catalog as the primary and authoritative source.
2. Add a bounded, cached disk catalog that reads only rollout metadata during discovery.
3. Reconcile both catalogs by native session ID without changing existing App Server rows.
4. Resume an App Server-readable session through the existing path.
5. For a disk-only session, run an on-demand compatibility probe.
6. When a tested migrator can normalize the complete model-visible history, create a current-format migration copy and continue there.
7. Otherwise keep the source visible and return a structured incompatibility result.

AgentRoam will not install and retain every historical producer runtime. The observed history contains too many stable and alpha versions for exact-version runtime selection to be operationally safe or maintainable. Compatibility is instead declared for tested schema generations against the currently selected reader and migrator set.

## Architecture

### Existing Primary Path

The current flow remains unchanged for sessions returned by App Server:

```text
codex app-server thread/list
    -> CodexRuntimeAdapter
    -> AgentWorkspaceIndex
    -> Desktop/Web renderer
```

### Additive Reconciliation Path

The disk catalog supplements only missing native IDs:

```text
CodexRuntimeAdapter thread/list result -----------+
                                                  +-> reconcile by nativeSessionId
CodexSessionDiskCatalog cached metadata ----------+        |
                                                           v
                                                  AgentWorkspaceIndex
```

Merge precedence is fixed:

- An App Server row wins every field collision.
- A disk row is emitted only when its native ID is absent from the App Server catalog.
- Existing sessions retain their current order, workspace assignment, status, occupancy, and capabilities.
- Supplemental rows use the same project-ID and longest-root `cwd` association already used by `AgentWorkspaceIndex`.
- A supplemental row without a matching workspace is placed in the existing Codex recent workspace.
- Disk scanning failure removes or stales only supplemental rows; it never fails the primary App Server list.

## Components

### CodexSessionDiskCatalog

`CodexSessionDiskCatalog` owns read-only filesystem discovery below the resolved session root. It does not parse conversation bodies during list operations.

For each regular `.jsonl` file it records:

- canonical path;
- file size and high-resolution modification time;
- native session ID;
- producer `cli_version`, when present;
- timestamp and `cwd`;
- source, thread source, history mode, parent/fork metadata when present;
- a lightweight header fingerprint derived from the `session_meta` record shape;
- scan status and a safe diagnostic reason.

The scanner validates real paths below the session root, rejects escaping symlinks, caps the metadata record read, and treats malformed files independently. One malformed rollout cannot abort the directory scan. When `session_meta` cannot be parsed, the scanner first derives the native ID from the strict Codex rollout filename shape. If no valid native ID can be recovered, it emits a stable catalog-only ID derived from the canonical path digest; that diagnostic row remains visible as incompatible but is never passed to an App Server operation.

Catalog rows are cached in broker-owned SQLite. The cache key includes canonical path, size, modification time, catalog schema version, compatibility-registry version, and selected reader version. Unchanged files require no content read on later scans.

### CodexCompatibilityRegistry

`CodexCompatibilityRegistry` contains only combinations proven by fixtures and runtime probes. It does not infer compatibility from semantic version ordering alone.

```ts
interface CodexCompatibilityRule {
  formatKey: string;
  producerVersions: string[];
  directReaderVersions: string[];
  migratorId?: string;
}
```

The initial header fingerprint selects candidate rules. Full compatibility is decided only after the selected reader or migrator validates the complete model-visible event stream.

Unknown versions may match an existing rule when their record structure is fully recognized and the rule explicitly permits structural matching. A new or unknown model-visible record type fails closed.

### CodexSessionMigrator

`CodexSessionMigrator` is invoked only after an explicit user request to continue a `migratable` session. It never modifies, renames, archives, deletes, or loads the source as a writer.

Migration stages are:

1. Produce a stable temporary snapshot. Compare source size, modification time, and content digest before and after copying. If the source changes, retry once; if it changes again, report that another client is actively writing.
2. Select the tested migrator by full schema validation.
3. Stream the snapshot into a version-neutral history representation.
4. Reject unknown model-visible records, broken tool-call/result relationships, or an incomplete terminal record.
5. Create a new thread with the selected current runtime.
6. Import normalized model-visible items through an App Server-supported import operation. Directly synthesizing or editing a current-version rollout file is forbidden.
7. Apply the title `<source title>（迁移副本）` and persist migration provenance.
8. Read the destination back through `thread/read`, validate it, and probe `thread/resume` before returning it as resumable.
9. Remove the temporary snapshot. On failure, delete the incomplete destination when possible and retain a failed migration record for diagnosis.

The selected reader must expose and pass a capability check for the import operation before any format rule can be marked migratable. For the current protocol this is expected to be `thread/inject_items`; its exact request and response schema must come from the selected runtime's generated schema and be covered by an integration test. If the capability is absent, the session is not migratable with that reader version.

### Migration Store

Broker-owned SQLite records migration state and makes the operation idempotent:

```ts
interface CodexSessionMigrationRecord {
  sourceSessionId: string;
  sourceDigest: string;
  sourcePath: string;
  producerVersion?: string;
  formatKey: string;
  targetSessionId?: string;
  readerVersion: string;
  migratorVersion: string;
  status: "preparing" | "importing" | "validating" | "ready" | "failed";
  reasonCode?: CodexCompatibilityReasonCode;
  reason?: string;
}
```

Repeating migration for the same source ID and digest returns the existing ready target. A changed source digest creates a distinct migration attempt and never mutates the earlier migration copy.

## History Semantics

Migration preserves all user-visible history and reconstructs the model-visible context needed to continue safely. The destination App Server must reproduce the normalized visible sequence through `thread/read`; AgentRoam does not use a private presentation sidecar to hide a lossy native import.

The neutral representation covers:

- ordered user and assistant messages;
- user-visible reasoning summaries; a source containing them is not migratable when the target schema cannot preserve them;
- tool calls, arguments, results, and stable call/result relationships;
- local image and supported attachment references;
- working directory, Git context, parent/fork provenance, and history-mode metadata;
- existing compaction or history-base records that a tested migrator understands.

Migration does not recreate executable transient state:

- historical commands are not run again;
- completed tools are not invoked again;
- old approval requests are not reopened;
- old process IDs and background terminals are not restored;
- hidden reasoning payloads are not exposed or imported;
- an in-progress partial turn is not represented as completed.

For context larger than the selected model window, migration uses the selected App Server's supported compaction behavior. Full user-visible history remains readable even though, as with native Codex continuation, the active model context can contain a compacted history base.

Missing local attachments retain an unavailable placeholder in display history. A migration may continue only when the missing asset was already non-model-visible or a tested history base proves that its content is no longer required. Otherwise validation fails with a specific incompatibility reason.

## Compatibility Contract

Add optional compatibility metadata so older renderer consumers remain valid:

```ts
type SessionCompatibilityStatus =
  | "checking"
  | "direct"
  | "migratable"
  | "incompatible";

type CodexCompatibilityReasonCode =
  | "CODEX_SESSION_VERSION_UNSUPPORTED"
  | "CODEX_SESSION_SCHEMA_UNKNOWN"
  | "CODEX_SESSION_DIRECT_READ_FAILED"
  | "CODEX_SESSION_IMPORT_UNAVAILABLE"
  | "CODEX_SESSION_MIGRATION_FAILED"
  | "CODEX_SESSION_SOURCE_ACTIVE"
  | "CODEX_SESSION_ASSET_REQUIRED"
  | "CODEX_SESSION_RUNTIME_UNAVAILABLE";

interface SessionCompatibility {
  status: SessionCompatibilityStatus;
  producerVersion?: string;
  readerVersion: string;
  formatKey?: string;
  reasonCode?: CodexCompatibilityReasonCode;
  reason?: string;
}
```

`UnifiedSessionSummary` gains optional `compatibility` and `migratedFrom` fields. Existing App Server rows omit `compatibility`; absence is interpreted as the existing direct behavior, preserving their serialized API shape. Supplemental rows initially use `checking` and `canResume: false` until an on-demand probe resolves them.

The existing generic runtime error union gains a structured version-compatibility code rather than mapping these failures to `NATIVE_PROTOCOL_ERROR`. Desktop IPC, broker socket responses, HTTP responses, and the renderer preserve the code and safe reason text.

## Data Flow

### Discovery

1. Return the last SQLite catalog immediately.
2. In parallel, run the existing App Server requests and an incremental disk reconciliation.
3. Merge by native session ID using App Server precedence.
4. Associate supplemental sessions through the existing workspace index.
5. Publish a refreshed catalog only when its generation is still current.

### Opening A Supplemental Session

1. Validate that the source path and metadata cache entry are still current.
2. Try `thread/read` by exact native ID with the selected runtime.
3. If the read and normalized detail validation succeed, mark the session `direct` and use the existing detail and continuation paths.
4. Otherwise validate the full stream against candidate migrators.
5. Mark it `migratable` only when one migrator consumes every required semantic record.
6. Otherwise mark it `incompatible` with the producer version, reader version, format key, and reason.

### Continuing A Migratable Session

1. The user invokes the explicit migration-copy action.
2. The broker serializes migration per source ID and digest.
3. The migrator runs the transaction described above.
4. A ready destination enters the normal App Server catalog and is selected through the existing refresh path.
5. The first new turn uses the unchanged `thread/resume` and `turn/start` flow.

## Performance Design

The list path never scans full histories. A local reference measurement contains 860 rollout files totaling approximately 3.9 GiB, including 102 files larger than 10 MiB and one file larger than 100 MiB. Reading only each first metadata record consumed approximately 25.9 MiB and 76 ms of raw sequential file time on the reference Mac. Full-history scanning on every refresh is therefore explicitly prohibited.

Performance controls are:

- cached rows render before background reconciliation;
- metadata reads use bounded concurrency, initially 16 files;
- each metadata read stops at the first newline and has a fixed safety cap;
- unchanged files are skipped by cache identity;
- filesystem notifications are debounced for 500 ms;
- a 60-second low-priority reconciliation repairs missed notifications;
- App Server listing retains 200-row cursor pagination;
- disk and App Server discovery run concurrently;
- full parsing occurs only for an opened supplemental session;
- migration uses streaming input and bounded buffers rather than `readFile`;
- migration reports progress and supports cancellation without affecting other sessions.

Reference-Mac acceptance budgets are:

- cached sidebar data available within 100 ms of catalog initialization;
- a cold 1,000-file metadata scan completes within 1 second;
- a normal incremental refresh completes within 200 ms when only a few files changed;
- migration adds no more than 64 MiB peak resident memory above the normal runtime baseline for a 100 MiB rollout.

Performance-budget failure does not hide primary App Server sessions. It marks the supplemental index stale and schedules a later retry.

## User Experience

- existing App Server row: render and behave exactly as today, with no compatibility field or badge.
- supplemental row resolved as `direct`: retain compatibility provenance internally but use the existing continuation behavior.
- `checking`: keep the session visible and temporarily disable continuation while the on-demand probe runs.
- `migratable`: show that continuing will create a migration copy; the original remains unchanged.
- `incompatible`: keep the session visible, disable continuation, and show the producer version, selected reader version, and specific reason.
- migration progress: show snapshot, import, and validation phases; allow cancellation before the destination becomes ready.
- migrated session: show the ordinary current-version session behavior and a concise `迁移副本` provenance label.

Runtime or compatibility-registry upgrades invalidate prior `checking` and `incompatible` cache decisions so affected sessions can be evaluated again. A prior incompatibility result is never permanent merely because it was cached.

## Safety And Failure Handling

- Every source path is resolved and verified below the configured session root before reading.
- Escaping symlinks, non-regular files, and files exceeding metadata safety limits produce isolated incompatibility rows.
- Source rollouts are never opened for write by the disk catalog or migrator.
- A source that changes during snapshotting is never migrated from an inconsistent copy. It remains `migratable` but temporarily blocked by the existing external-occupancy presentation rather than being permanently classified as incompatible.
- Unknown non-semantic metadata can be retained as opaque provenance; unknown model-visible semantics fail closed.
- Imported commands, tools, approvals, and process metadata are inert history.
- Partial destination cleanup never targets the source and is restricted to the exact returned destination ID.
- A disk catalog exception cannot reject the primary App Server request.
- Error responses do not expose raw rollout contents, credentials, injected instructions, or unrestricted filesystem paths.

## Rollout

### Phase 1: Shadow Catalog

Run the disk catalog and reconciliation without emitting supplemental rows. Record aggregate counts for disk IDs, App Server IDs, missing IDs, malformed metadata, scan duration, and cache hits. Do not record conversation content or full paths.

### Phase 2: Visible Compatibility State

Emit supplemental rows as `checking`, support direct-read probes, and show incompatible reasons. Migration remains disabled. Existing App Server rows must remain byte-for-byte equivalent at the API boundary.

### Phase 3: Tested Migration Generations

Enable migrators one format generation at a time after fixtures, runtime import, round-trip, and continuation tests pass. Formats without an enabled rule remain visible and incompatible.

### Phase 4: Default Availability

Remove internal rollout gating only after performance budgets, source immutability checks, and existing native-session regression suites remain stable on supported macOS and Windows targets.

## Verification

### Regression Coverage

- Existing App Server discovery produces the same sessions and existing fields before and after reconciliation.
- App Server and disk rows with the same native ID never duplicate.
- Existing workspace ordering, recent-workspace behavior, session sorting, pagination, selection, occupancy, fork, deletion, goals, permissions, and live-follow tests remain green.
- Missing, disabled, failed, or stale disk indexing leaves existing sessions operational.

### Compatibility Fixtures

Maintain sanitized fixtures for representative `0.122.x`, `0.13x`, `0.14x`, and `0.15x` stable and alpha schema generations. Cover additional and missing metadata fields, ordinal records, history bases, parent sessions, forks, dynamic tools, attachments, malformed JSONL, truncated final records, and unknown semantic events.

Fixture provenance records the producer version and expected format key. Compatibility rules cannot be enabled without at least one successful read or migration fixture and one rejection fixture for that generation.

### Migration Verification

- Source size, timestamps, and digest remain unchanged.
- User and assistant message order and normalized content match.
- Tool calls and results remain paired and ordered.
- Required attachments are copied or produce the correct failure.
- Compaction/history-base behavior preserves a resumable model context.
- Destination `thread/read` returns the expected history.
- Destination `thread/resume` succeeds.
- The first new user turn completes through the existing run path.
- Cancellation and injected failures leave no selectable partial destination.
- Repeating a successful migration for the same digest returns the same target.

### Performance Verification

Use a generated directory with approximately 1,000 files and 4 GiB of aggregate history. Measure cold metadata indexing, warm cache startup, small incremental updates, a 100 MiB streaming migration, cancellation, and simultaneous normal App Server use. Reject an implementation that meets functional tests by reading every rollout body during discovery.

### Real Acceptance

On a supported Mac with multiple producer versions:

1. Existing current-format sessions retain identical behavior.
2. A disk-only directly readable session becomes direct after probing and resumes in place.
3. A tested legacy format creates a labelled migration copy whose first new turn completes.
4. An unsupported semantic format remains visible with a version incompatibility reason.
5. An externally active source cannot be migrated from an unstable snapshot.
6. Restarting AgentRoam preserves catalog and migration state without duplicating rows or targets.

## Non-Goals

- Installing every historical Codex CLI or Desktop runtime.
- Claiming compatibility based only on producer semantic-version ordering.
- Editing or upgrading source rollout files in place.
- Restoring historical process IDs, running terminals, unresolved approvals, or hidden reasoning.
- Automatically migrating a session without an explicit continuation action.
- Changing archived-session visibility.
- Changing non-Codex runtime adapters.
